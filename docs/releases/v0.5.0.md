# Skynet-EDR v0.5.0 — bounded S3 Hermes enrollment

Skynet-EDR v0.5.0 is a passive Linux-first **prerelease** for evaluation and controlled lab use. It is not production-supported and does not block agent actions.

## Implemented scope

This release carries forward the v0.4.1 passive detection, redaction, local evidence, and read-only visibility baseline. It adds a fail-closed S3 enrollment transaction for the exact exercised compatibility cell: Ubuntu 24.04 `x86_64`/`amd64`, systemd, Hermes `0.19.0`, and the Skynet-EDR `0.5.0` plugin in Hermes' `default` profile at the exact `<passwd home>/.hermes` path.

S3 validates the package-owned plugin payload, stages and publishes it transactionally, prepares the bounded daemon and Hermes configuration, and attests the exact restarted processes and protocol-v3 producer. Successful attestation requires fresh process identities, an independent plugin runtime nonce, healthy source state, and an exact persisted harmless canary receipt with no incident.

## Install and artifact verification

Download the selected artifact and `checksums.txt` from the same release. Verify the checksum before installing; do not use an unverified `curl | sudo sh` path.

```bash
sha256sum -c checksums.txt --ignore-missing
sudo apt install ./skynet-edr_0.5.0_amd64.deb
skynet-edr --version
skynet-edr doctor
```

Artifact signing, SBOM, and provenance attestation are not yet production release guarantees. Check that the verified artifact basename, architecture, and reported binary version match this release.

## Upgrade and rollback

Preserve `/etc/skynet-edr/`, `/var/lib/skynet-edr/`, and `/var/lib/skynet-edr-hermes-enrollment/` before upgrading. Stop the service, install the verified v0.5.0 package, then run the documented health and enrollment checks. To roll back, stop the service, install a previously verified package, and restore state only when its documented schema requires it. Package upgrade and rollback remain operator procedures rather than production-qualified runtime guarantees.

Enrollment rollback authority and evidence are retained in the private enrollment state. Do not delete or rewrite that state during recovery.

## S3 quarantine and manual recovery

Unenrollment and unsafe partial states use same-filesystem, no-replace, non-destructive quarantine. Managed backend, Desktop, metadata, observation, and rollback evidence are retained with a durable exact-schema transaction journal. No successful, failed, repeated, or crash-recovery path automatically purges quarantined content.

A root operator must inspect journal identities, ownership, modes, names, and digests before manually restoring an identity-matching quarantined object to an absent source. Plain overwrite, recursive deletion, and path-following recovery are unsupported. See [Hermes enrollment](../HERMES_ENROLLMENT.md) for the exact procedure.

## Threat boundary and limitations

The target numeric UID and its Hermes home/profile are hostile. The privileged enrollment process and its private root-owned mode-`0700` state and quarantine tree are trusted for S3. Same-UID tampering is prevented from becoming a privileged path escape and causes verification or rollback to fail closed.

S3 does not defend an already validated private parent path against unsynchronized concurrent replacement by another hostile UID 0 actor. Hostile concurrent root replacement and descriptor-relative `mkdirat`/`openat` hardening are deferred to S4. Root automation must serialize through the managed lock.

Restart authorization restarts the complete `user@UID.service`, not only Hermes. Every user service managed for that account may be interrupted and restarted; operators must accept this account-wide availability blast radius explicitly.

Release promotion requires the exact release SHA to pass the documented disposable clean-host gate for the Hermes CLI/read-back and booted-systemd flow; deterministic fixtures alone are insufficient. Other distributions, architectures, init systems, Hermes versions, custom profiles/homes, dashboard-only runtimes, and global-role setups are unsupported or unproven and fail closed.
